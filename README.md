# TypeScript coding agent harness

Консольный агент для задания «Coding agent с tool calling», реализующий требования уровней 7–10. Модель выбирает инструменты и момент завершения; собственный runtime отвечает за policy, подтверждения, сохранение, восстановление, бюджеты, задачи и откат. Готовые агентские фреймворки не используются.

## Установка и проверка

Нужны Node.js **22.13+** (рекомендуется актуальная версия ветки 22), npm, Bash и Python 3.9+. На Windows используйте WSL. `node:sqlite` в Node 22 может печатать предупреждение ExperimentalWarning; дополнительный SQLite-сервер не нужен.

```bash
git clone https://github.com/StreveSuksess/ts-agent-harness.git
cd ts-agent-harness
npm ci
npm run check
npm test
npm run demo
```

`workspace/order.py` намеренно содержит исходную ошибку. `workspace/test_order.py` — контрольные тесты задания. Тесты runtime и offline demo работают с отдельными копиями: файлы сдаваемого примера остаются исходными.

`npm run demo` не требует API и явно использует **подставную модель** с заданными ответами. Инструменты, исполнение Bash, SQLite, проверки результата и снимки файлов настоящие. Demo печатает run_id, путь к отдельной базе, чеклист трёх зависимых задач, вывод Bash, diff и бюджеты. Это воспроизводимая проверка runtime, а не доказательство поведения настоящей LLM.

В среде с корпоративным сертификатом Node иногда не доверяет цепочке, которой доверяет macOS. На Node 22.19+ можно установить зависимости с системным хранилищем CA: `NODE_OPTIONS=--use-system-ca npm ci`. Проверка TLS не отключается.

## Настоящая модель

Поддерживается OpenAI-compatible **Chat Completions API с tool calling**. Клиент реализован через `fetch`; ключ не сохраняется в SQLite и не передаётся дочернему Bash. Скопируйте `.env.example` в `.env`, задайте адрес, ключ и имя доступной модели. `.env` исключён из Git и автоматически читается командой `npm run agent`.

Учебный/корпоративный сервис с совместимым API подходит. Для уже установленной Ollama пример настройки соответствует заданию:

```bash
ollama pull qwen3:4b
ollama serve
```

```dotenv
OPENAI_BASE_URL=http://localhost:11434/v1/
OPENAI_API_KEY=ollama
OPENAI_MODEL=qwen3:4b
```

Создайте учебную копию проекта и запустите агент:

```bash
mkdir -p .agent
HARNESS_WORKSPACE=$(mktemp -d .agent/live-XXXXXX)
cp -R workspace/. "$HARNESS_WORKSPACE"
npm run agent -- start --workspace "$HARNESS_WORKSPACE" --policy policy.example.json --mode auto --task "Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты."
```

Команда напечатает `run_id`. По умолчанию сначала используется Plan Mode. В примерах ниже заменяйте `RUN_ID` этим идентификатором; не создавайте новый запуск для продолжения старого.

```bash
npm run agent -- status RUN_ID
npm run agent -- approve-plan RUN_ID --decision approve
npm run agent -- tasks RUN_ID
npm run agent -- diff RUN_ID
```

Отказ от плана: `approve-plan RUN_ID --decision reject`. Модель получит отказ и сможет предложить другой план. `--no-plan` запускает исполнение без отдельной планирующей фазы; runtime создаёт одну задачу, требующую успешного `python3 -m unittest -v` как подтверждения. Для демонстрации уровня 9 используйте обычный Plan Mode с тремя задачами.

## Инструменты и цикл

| Инструмент | Аргументы | Результат |
|---|---|---|
| `list_files` | `path` | разрешённые имена файлов/директорий |
| `read_file` | `path` | текст, хеш, признак обрезки |
| `write_file` | `path`, `content` | создание/замена UTF-8 файла, хеш |
| `delete_file` | `path` | удаление одного обычного файла |
| `Bash` | `command`, `cwd` | stdout, stderr, exitCode, timedOut, truncated |
| `submit_plan` | `plan` | сохранение структурированного плана и ожидание пользователя |
| `complete_task` | `evidence_call_id` | проверка свидетельства и завершение текущей задачи |

Каждый инструмент передаётся с именем, описанием и JSON Schema. Ajv проверяет аргументы; policy повторно проверяется непосредственно перед исполнением. Несколько проектных tool calls в ответе поддерживаются и исполняются последовательно. `submit_plan` и `complete_task` должны быть отдельными вызовами, чтобы переход фазы/задачи не изменял смысл остальной пачки.

Ошибки инструментов возвращаются модели через `role: tool` с исходным `tool_call_id`. Законченный вызов с тем же ID и аргументами возвращает сохранённый результат. Изменение имени/аргументов при том же ID, включая повтор в одной пачке, даёт ошибку протокола. Новая задача должна использовать новые ID вызовов. Модель завершает работу текстовым ответом; успешный статус допустим только после завершения всех задач с подтверждениями.

## Policy и режимы

`policy.example.json` находится вне workspace. Пути в `directories` задаются относительно выбранного workspace и проверяются канонически. Запрет приоритетнее разрешения; неизвестные команды/директории отклоняются.

В примере разрешены `python3 -m unittest -v` и `python3 -B -m unittest -v`; запрещены `rm -rf .` и `bash -c echo`. `pwd` включён одновременно в allow и deny, демонстрируя приоритет deny. Разрешена директория `.`, запрещена `restricted` со всеми потомками. `test_order.py` защищён от прямой записи/удаления файловыми инструментами.

Bash принимает только точные команды из allow и ограниченный синтаксис bare words. Запрещены пайпы, перенаправления, кавычки, подстановки, переводы строк, присваивания, вложенные shell-команды, `-c` и пути в аргументах. Для проекта с иной командой тестов измените allow вне workspace. Bash действительно запускается через `/bin/bash --noprofile --norc -c`; окружение ограничено PATH, LANG и PYTHONDONTWRITEBYTECODE. BASH_ENV, API-ключи и другие переменные не наследуются. Вывод непрерывно читается с ограничением сохранённых байтов; таймаут завершает группу процессов.

Все файловые аргументы и cwd — относительные пути. Абсолютные пути, компоненты `..`, симлинки, hardlinks и специальные файлы отклоняются. `write_file` требует существующую родительскую директорию. Снимки также отклоняют ссылки и специальные файлы.

| Режим | Чтение | Запись и Bash | Удаление |
|---|---|---|---|
| `safe` (по умолчанию) | сразу | после подтверждения | после подтверждения |
| `auto` | сразу | сразу после проверок | после подтверждения |

В `safe` агент сохраняет ожидаемый вызов и **останавливает процесс**, не ждёт stdin. Продолжение или отказ — отдельная команда:

```bash
npm run agent -- approve-action RUN_ID --decision allow
npm run agent -- approve-action RUN_ID --decision deny
```

Эти команды сохраняют решение и продолжают тот же запуск. После отказа модель получает причину. Утверждение плана не утверждает опасные действия в safe. Изменённая пользователем policy перечитывается перед исполнением уже подтверждённого действия.

Policy **не является изоляцией ОС**. Разрешённые Python-тесты и импортируемый проектный код исполняются с правами пользователя и могут обращаться вне workspace. Проверка readOnlyFiles защищает файловые инструменты, а не произвольный код Python. Используйте учебную копию без секретов; для недоверенных проектов нужен отдельный контейнер/пользователь. Проверки путей и дескрипторов уменьшают риск обхода, но не обещают защиты от внешнего процесса, меняющего дерево между проверками.

## Plan Mode и задачи

До утверждения разрешены только `list_files`/`read_file` и административное сохранение плана. Ни Bash, ни запись, ни удаление не исполняются. JSON-план содержит:

```json
{
  "goal": "Исправить расчёт заказа",
  "steps": [
    {"id":"inspect","description":"Прочитать реализацию","depends_on":[],"tools":["read_file"],"verification":{"kind":"tool","tool":"read_file"}},
    {"id":"fix","description":"Исправить формулу","depends_on":["inspect"],"tools":["write_file"],"verification":{"kind":"file_changed","path":"order.py"}},
    {"id":"verify","description":"Проверить тесты","depends_on":["fix"],"tools":["Bash"],"verification":{"kind":"bash","command":"python3 -m unittest -v","exitCode":0}}
  ],
  "risks": ["Проверить недопустимые значения скидки"],
  "assumptions": ["Цены числовые"],
  "done_when": "Тесты проходят, test_order.py не изменён"
}
```

Runtime проверяет уникальность ID, зависимости и отсутствие циклов. После утверждения последовательно выбирается готовая задача. Каждый проектный вызов на исполнении связан с её task_id; вызовы планирования имеют task_id=null. Инструмент должен быть объявлен для этой задачи.

`complete_task` принимает ID уже сохранённого успешного вызова из текущей задачи. Runtime проверяет конкретный тип инструмента, фактическое изменение файла либо команду и exitCode Bash. Для Bash также проверяется, что дерево после тестов не изменилось; старый успешный тест после новой правки не принимается. Свидетельство сохраняется в задаче. Чеклист stdout: `[ ]` ожидает, `[>]` выполняется, `[x]` подтверждена. После resume завершённые задачи не запускаются заново.

## Хранилище и сбои

По умолчанию SQLite расположен в `.agent/state.sqlite`, вне изменяемого workspace. Любая команда принимает `--db PATH` для другого хранилища. Для одного workspace используйте одно хранилище: блокировка рядом с БД исключает конкурирующее исполнение в этой области хранения. Оптимистическая проверка revision предотвращает потерю обновлений состояния.

Транзакции SQLite с WAL и synchronous FULL сохраняют историю, пачку вызовов, попытки, результаты, решения, задачи, бюджеты и снимки. Перед исполнением инструмента записывается started и резерв вывода. После исполнения результат, фактический снимок, diff, счётчики и tool-сообщение сохраняются вместе.

```bash
npm run agent -- resume RUN_ID
```

Если процесс упал после started, но до записи результата, resume переводит вызов в `uncertain` и **ничего не повторяет**. Просмотрите состояние и найденные изменения:

```bash
npm run agent -- status RUN_ID
npm run agent -- diff RUN_ID
npm run agent -- resolve RUN_ID --decision fail --attribute yes
```

При обнаруженных изменениях `--attribute yes|no` обязателен: пользователь явно решает, относятся ли изменения к этому запуску. `yes` включает их в журнал; `no` не включает. Разрешение возможно после resume, переведшего начатый вызов в uncertain.

Другие варианты: `--decision retry` или `--decision abort`. Retry оформляет **новую попытку того же call ID**, тратит новые ресурсы и разрешён только для read/list и записи тех же данных в тот же файл. Запись повторяема после явного принятия текущего дерева и проверки policy. Bash и удаление не считаются безопасно повторяемыми; для них выберите fail или abort. Потраченный до сбоя бюджет не возвращается.

Управляемые точки отказа: `--fault after_reservation`, `--fault after_execute` и `--fault after_rollback_write`. Первая находится после сохранения started/бюджета, вторая после исполнения и до сохранения результата. CLI завершится с ошибкой, а база сохранит начатую попытку. На resume не передавайте --fault. Детерминированные тесты специально вызывают сбой после изменения order.py и проверяют восстановление.

## Бюджеты

Поля `budgets` в policy: modelRequests, toolCalls, sideEffects, resultBytes. Лимиты копируются при создании запуска и сохраняются с ним. Изменение policy, plan approval и resume не обнуляют и не увеличивают лимиты этого run_id.

- Запрос к модели списывается до отправки; ошибка API тоже расходует запрос.
- Вся пачка tool calls допускается или отклоняется целиком. Счётчик вызовов и резерв действий сохраняются с пачкой.
- Side effects резервируются для всей пачки, но списываются как исполненные при started. Отказ/валидационная ошибка до started освобождает неиспользованный резерв; начатая попытка не возвращается после сбоя.
- Инструмент получает доступный остаток вывода, ограниченный maxOutputBytes. Перед started этот объём резервируется атомарно. При обычном завершении сохраняется фактический размер UTF-8 JSON и освобождается неиспользованная часть. После сбоя весь списанный резерв остаётся потраченным.
- Обрезанный результат остаётся валидным JSON с `truncated:true`; метаданные проверки задачи сохраняются отдельно от сокращённого сообщения модели.
- Исчерпание лимита останавливает запуск со статусом blocked. Resume не возобновляет запуск с исчерпанным бюджетом. Для новой попытки нужен новый run_id.

Повторная доставка кешированного результата не запускает инструмент, но расходует байты доставленного результата и новый tool call. Ручной просмотр/откат — команды пользователя, а не инструменты модели; они доступны даже при исчерпанном бюджете.

## Diff и безопасный откат

```bash
npm run agent -- diff RUN_ID
npm run agent -- rollback RUN_ID
```

Перед каждым потенциально изменяющим действием, включая Bash, runtime сравнивает полное дерево с последним сохранённым состоянием и сохраняет снимок в попытке. После действия сохраняется реальное дерево и diff. У каждого затронутого файла хранятся содержимое и режим до первого изменения, после последнего изменения и SHA-256. Создание и удаление также учитываются. Исключений для генерируемых файлов нет; Python bytecode отключён через окружение Bash.

Перед rollback проверяются policy, пути и **все** текущие хеши/режимы затронутых файлов. При одном конфликте не восстанавливается ни один файл. Нетронутые файлы, включая созданные пользователем после запуска, сохраняются. Журнал работает после перезапуска БД. Diff показывает исторические изменения, отнесённые к запуску, и отдельно неопределённые изменения до их атрибуции.

Если rollback сам был прерван, его started-состояние сохраняется. После resume обычное исполнение блокируется; команда `resolve-rollback RUN_ID` явно завершает восстановление только после проверки, что каждый файл соответствует сохранённому before или after. Любая третья версия вызывает конфликт до новых записей.

Восстановление нескольких файлов не является одной транзакцией файловой системы. При сбое посреди него нужна явная команда выше. Полные снимки рассчитаны на небольшие учебные проекты; размеры одного файла/дерева ограничены policy, а накопленная история растёт с числом попыток.

## Структура и защита

- `src/runtime.ts`: цикл и сохранённые переходы состояния.
- `src/policy.ts`, `src/schema.ts`: ограничения и JSON Schema.
- `src/tools.ts`: реальные файловые операции и ограниченный Bash.
- `src/store.ts`: SQLite и блокировка workspace в области хранилища.
- `src/journal.ts`: полные снимки, diff, preflight и восстановление.
- `src/model.ts`: API-клиент и подставная модель для проверок.
- `src/cli.ts`, `src/demo.ts`: CLI и явно обозначенная offline демонстрация.
- `tests/`: ограничения, подтверждения, сбои, бюджеты, план, задачи, журнал и API-контракт.
- `docs/spec.md`, `docs/superpowers/plans/`: требования и план реализации.

Для 20-минутной защиты: запустите `npm run demo`, покажите переход Plan → approval → три задачи и результат Bash. Затем выполните `npm test` и объясните проверки отказов, обе точки сбоя, отсутствие повторов, счётчики после resume и отказ rollback при чужой правке. При доступной настоящей модели отдельно покажите описанный live-запуск.

Репозиторий приватный: до защиты предоставьте преподавателю доступ. Не публикуйте `.env` или `.agent`: SQLite содержит прочитанные файлы и историю запуска.

## Проверенная граница

Локально проверены строгая компиляция, автоматические тесты и offline demo. Отдельный интеграционный тест запускает CLI в нескольких процессах через настоящий HTTP-клиент с подставным API, проверяет последовательность tool-сообщений и откат после перезапуска. Проверка с настоящей LLM пока не выполнена: в исходной среде нет настроенного API и установленной/запущенной Ollama. Перед защитой нужен live-запуск по инструкции выше.
